### 标题（二选一）

### 正文

今年在准备 2027 年的美国 J-1，全程自己申，没找中介。

一开始只是想搞清楚一件事：我这个情况到底能不能申、能申哪几个。结果查了两周，越查越乱——同样是打工度假，有的国家对中国大陆护照开放，有的只开到中国台湾和中国香港；有些公众号文章写得斩钉截铁，翻到官方页面发现根本没这句话；还有的攻略是三年前的，签证费早就变了。

最难受的不是信息少，是**分不清哪条还能信**。

后来我换了个做法：不再攒文章，而是把每个项目当成一条数据来记——这个项目对哪本护照开放、年龄上限多少、要不要语言成绩、费用多少、什么时候开窗口，**每一条都记下它是从哪个官方页面看到的、哪天看的**。查不到的就老实写「未核实」，不猜一个看起来合理的数字。

攒下来是 41 个项目，覆盖 21 个国家和地区，其中中国大陆护照能申的是 34 个，剩下 7 个是不能申的。

那 7 个我也留下了。因为中文互联网上最大的坑就是把「中国台湾/中国香港可申」写成「中国可申」，加拿大 IEC、英国 YMS、爱尔兰 WHA、日本 WH、韩国 H-1 都是双边协议，中国大陆护照不在名单里。与其让人花三个月准备材料最后发现根本不接受，不如一开始就说清楚：这几个不能申，原因是这个。

后来给它加了两个我自己的需求：

**一是保鲜。** 每个项目都记着上次核实的日期。窗口写死到具体日期的项目 90 天复核一次（一年只开一次窗，错过等一年），其余 180 天。超期了会自动开一张 issue 把该核的列出来——不是提醒我一下就算了，是列成清单。

**二是能筛。** 做成了一个网站，可以按国家、按项目类型、按护照资格筛，也能直接搜。中英双语，手机上能用。

现在这个库是开源的，41 个项目一共 136 条来源，每条都指到具体页面。它不是攻略，更像一份「可以被查证」的清单——你觉得哪条不对，可以点页脚的「发现数据有误？提纠错」，附上官方链接，我会去核。

链接放评论区。如果你也在查这类项目，欢迎拿它当起点，但**申请前一定自己再点开官方页面确认一遍**——我能保证的是「我核过并记了日期」，不能保证「政策不会变」。

### 正文

```
做这个小东西的起因很具体：在给自己查 2027 年 J-1 的资格，发现中文世界关于「打工度假 / 海外实习签证」的信息有一个系统性问题——
把只对中国台湾、中国香港护照开放的项目，写成「中国公民可申请」。加拿大 IEC、英国 YMS、爱尔兰 WHA、日本 WH、韩国 H-1 都属于双边互惠协议，中国大陆护照不在名单内。这类错误在攻略、中介软文、AI 生成内容里反复出现。

于是我把它当成一个数据工程问题来做，而不是又一个攻略站。

是什么
开源数据集 + 一个双语静态站。41 个项目、21 个国家和地区、136 条来源，其中中国大陆护照可申 34 个、不可申 7 个（不可申的也明确收录，作为排除记录）。
站：https://eddieye1004.github.io/overseas-program-dataset/
库：https://github.com/eddieye1004/overseas-program-dataset

怎么做的

1) schema 先行。每个项目一个 JSON，字段定义在 data/schema.json，护照资格是第一等公民（passport_types 决定 90% 的结论）。

2) 来源分级 + CI 强制。每条来源标 primary/secondary，并按域名分 A/B/C/D 四级：A 是移民局/使领馆/官方法规库，D 是百科、自媒体、商业博客。D 级出现即 CI 失败，全部来源都不到 A/B 级也失败。二手来源不能单独支撑硬性资格判定。

3) 保鲜靠台账而不是靠人记。每条记录带 last_verified。scripts/track.py 按项目性质分档：窗口写死到具体日期的 90 天复核、其余 180 天，剩余不足 25% 提前标「即将到期」。
产物两份：tracking.json 给程序读，FRESHNESS.md 给人读。CI 每周一跑 --check，超期即退出码 1 把构建打红；另有一个脚本把同一份台账同步成一张 issue（固定标题 + 固定标签，先搜后改，不刷屏），让「红了」这件事真的有人看到。

4) 配额四态化（刚做完的一轮）。原来是「整数或 null」，而 null 同时兼指「无名额上限 / 官方设限额但未公布 / 还没查」三种，29 个项目里 26 个都是 null，读的人分不出来。
现在改成一个必填的状态字段，四态：有具体配额 / 无配额 / 官方未公布数字 / 待核实。凡断言前三态都必须指向本项目已有的一条 primary 来源，指不出来就只能写「待核实」。当前分布 4 / 34 / 1 / 2。
两条「待核实」我没有硬凑数字——一个是奥地利红白红卡高资质档，法规说受年度配额约束但公开页面找不到数字；一个是德国机会卡，法条授权联邦政府可限量但截至核实时没见到生效公告。这两条就挂在待办清单里。

现在的状态
validate 严格模式 0 错 0 警；118 个 Python 测试；e2e 203 条断言；前端 tsc/smoke/build 全绿。
没有 star 数可以报，也没有用户量可以报——就是我自己在用的一个库。

想求什么反馈
1) 数据纠错入口刚上线（结构化 issue 表单，必填官方来源），最想要的是**挑错**：哪条资格写错了、哪条链接死了、哪个数字过期了。附上官方页面链接就行。
   表单：https://github.com/eddieye1004/overseas-program-dataset/issues/new?template=data-correction.yml
2) 来源分级的标准是否合理——特别是「高校官方部门算 C 级、只能作旁证」这条，我拿不准是不是过于严格。
3) 如果你在做同类项目，想听你怎么解决「保鲜」这件事。

不做的事也写清楚：不代办、不做中介导流、不提供「你该申哪个」的建议。这是信息汇编，判断留给你自己。
```

### 开头两段（成品文）

```
去年冬天我第一次认真查美国 J-1 的时候，遇到了一件很小但很困扰的事：同一个「暑期带薪实习」项目，我看到了几种不同的说法。

一种说年龄 18 到 28 岁；一种说没有年龄限制；一种说要看具体 Sponsor；还有一种直接引用了某高校国际处的页面，写着「18-28 周岁」。我把美国国务院的项目页和 22 CFR 62.32 的条文都翻了一遍，页面正文里检索「years of age」，命中为零；页面源码里出现的「18」和「28」，逐个看过去都是 CSS 渐变角度和一个电话号码，不是年龄条款。

那「18-28」是哪来的？来自一所高校国际处的工作说明。它没有错，它描述的是中方合作机构的实际操作口径。但它在传播中被当成了「美国官方的规定」。这两者的差别，足以让一个 29 岁的人放弃申请，或者让一个 17 岁的人白准备材料。

这件事让我意识到，我面对的不是「信息不够」的问题，而是「信息无法被判定」的问题。攻略、中介软文、AI 生成内容、高校通知、官方页面，它们在同一个搜索结果里并排出现，长得一样，语气都很确定。读者没有工具去区分「这条有官方依据」和「这条是别人转述的」，更没有工具去知道「这条是什么时候核的」。
```

### 后续段落写作要点（给终稿用）

**§1 问题不是信息少**
- 三类错位各举一例（身份 / 时间 / 来源），每例都要能点回具体页面。
- 关键论点：错位的成本由读者承担——他们花的是几个月时间和一次机会。
- 不要写成「中文互联网很糟」这种泛论，只写机制。

**§2 把项目变成记录**
- schema 先行：字段定义比数据本身更重要，因为它决定了「什么算填完了」。
- 护照资格当第一等公民：因为它是唯一能一票否决的维度。
- 收录「不可申」的理由：排除性信息同样是信息，而且更稀缺——没人愿意写「你不能申」。
- 要点：41 个项目里 34 个可申、7 个不可申，不可申的那 7 个恰恰是被误传最多的。

**§3 来源分级**
- A/B/C/D 的定义与判据（政府/项目本体/高校与其他可核验机构/百科自媒体）。
- 为什么 D 级「出现即失败」而不是「降权」：混入一条就无法再声称每条可追溯。
- 为什么二手来源不能单独支撑硬性结论：转述会丢上下文。
- CI 如何强制：不靠人自觉，靠流水线。
- 136 条来源的分布可以放，但避免把数字当卖点。

**§4 保鲜机制**（本文最核心的方法论段落）
- 核心洞察：数据会过期，但「过期」不是一个状态，是一个**时间函数**——所以要给每条记录一个周期，而不是给整个库一个免责声明。
- 周期分档的依据：窗口写死日期的项目一年只开一次，晚一周可能白等一年，所以 90 天；其余 180 天。
- 两层动作：让构建变红（硬信号）+ 自动开 issue（给人看的待办）。为什么光变红不够——定时任务没人推，红一次就被无视。
- 幂等的重要性：固定标题 + 标签，先搜后改，不刷屏。这是「自动化不打扰人」的基本礼貌。

**§5 把「不知道」变成状态**
- 讲清楚原罪：一个 nullable 字段被用来表示三种完全不同的含义，读者无法区分，也无法据此排待办。
- 四态设计与证据约束：凡断言必须有来源，指不出来就只能写「待核实」。
- **重点写两条「待核实」的取舍**：明知读者想看数字，但硬填一个数字的代价是让整个库的可信度打折。这是全文最能体现方法论的地方——克制也是一种功能。
- 分布 4/34/1/2 可以给，但要说明「34 个无配额的里，有一部分是官方不设上限，另一部分是中国大陆护照根本不分配名额」——这两件事在旧表示法里长得一模一样。

**§6 开放纠错**
- 门槛前置而非事后评审：把「必须附官方来源」写进表单必填项。
- 为什么用结构化表单而不是自由文本框：减少来回追问的轮次。
- 边界：接受纠错，但不接受「我觉得应该是」——没有来源的意见无法进入数据层。

**§7 边界**（少数派读者最吃这一段，不要略写）
- 能保证的：每条结论有可点的来源、每个数字有核实日期、不能申的项目被明确写出。
- 不能保证的：核实日之后的政策变化、覆盖的完整性、对个案的适用性。
- 单人维护的可持续性：这是真实的弱点，写出来比藏起来好。保鲜机制某种程度上就是为了缓解这一点——让机器提醒人，而不是靠人记得。

**§8 结尾**
- 回到方法：这套「记录 + 来源 + 周期 + 显式未知」的结构，可以搬到任何会过期的信息领域（房价政策、考试简章、医保目录）。
- 不写「欢迎 star」，写「欢迎拿这套结构去做你自己的那份」。
