## 0. 一句话结论

C 画像的 14 个「不可判」不是同一种东西：**3 个是设计上就该判不可判（甲类）**，**11 个是数据/画像缺口造成、可修的债（乙类）**。把两条分开后，C 的**乙类不可判率 = 11/41 = 0.2683，低于 1/3**；当前 CI 那条红是**度量口径把两类混算**的结果，不是判定行为变坏。建议：**阈值 1/3 一个数字都不动，只把闸门的分子换成乙类**，甲类单列报告不设硬闸、但设一条 5 项的观察线。

## 1. 14 个不可判逐项分类

### 1.1 分类判据（先定标准，再分类）

两类不能用「感觉像不像缺陷」来分，否则第 4 节说的滥用口子立刻成立。本提案用一条**可机械执行**的判据：

> **甲类（设计性不可判）**：这条要求的内容，**在「项目数据层」与「用户画像层」都不存在可承载它的字段**；即使把两层的字段加满、数据补齐，仍然判不了，只能替官方/Sponsor 做一次主体性判断。
>
> **乙类（可避免不可判）**：这条要求**可以用现有字段、或一条能明确定义的新字段完整表达**；当前判不了，是因为数据没登记、画像没采集、或换算表没建。每一项都能写出一条具体的「补什么就能判」。

推论（这是后面所有条目的判法）：

1. 「官方根本没公布阈值」→ 甲类。没有任何数字可抄，补数据只能补某个机构/某个 Sponsor 的口头答复，而那不能冒充项目级规则。
2. 「官方公布了阈值，但仓内 `tests: []` 没登记」→ 乙类。字段在那儿空着。
3. 「要求是外部机构对**个人**的一次评价（学历认定）、由 Sponsor 逐人判断」→ 甲类。评价结论不是项目属性，也不是画像属性，加字段只是把 note 抄一遍。
4. 「要求是画像没采集的个人事实（现居地、毕业年份、年收入、院校）」→ 乙类。加画像字段即可判。
5. **混合项**（同一项目既有甲因又有乙因）→ **一律计入乙类**。理由：只要还有一条可修的债，这个项目就仍欠一次修复；若按「全部原因是甲才算甲」的反向规则，`de-chancenkarte` 会因为「认定」是甲而把一个明显可修的 CEFR 缺口洗成设计性——那正是要堵的口子。这条规则写在第 3 节的测试里。

## 2. 新停工线公式提案

### 2.1 精确定义

设 `P` = `data/programs/*.json` 的项目全集（当前 `|P| = 41`），`S` = 三样例画像 `{A, B, C}`，
`dims(p, s)` = `judge(p, s)` 返回的逐维结论，`BY_DESIGN` = 甲类 code 白名单（当前 `frozenset({"edu_by_sponsor", "age_unknown"})`）。

```
可修(p, s)  :=  state(p, s) == "unknown"
              ∧ ∃ d ∈ dims(p, s) : d.kind == "silent" ∧ d.code ∉ BY_DESIGN

乙率(s)  :=  |{ p ∈ P : 可修(p, s) }| / |P|
甲率(s)  :=  |{ p ∈ P : state(p,s)=="unknown" ∧ ∀d∈dims(p,s), d.kind=="silent" ⇒ d.code ∈ BY_DESIGN }| / |P|

停工  :=  max_{s ∈ S} 乙率(s) > 1/3          ← 硬闸，越过即停工报 Muse
报警  :=  max_{s ∈ S} 甲率(s) ≥ 5/41         ← 软线，不红，只要求人在报告里解释
```

四个定义上的取舍，逐条说明为什么这样定：

1. **分子按「项目」计，不按「原因」计。** 理由沿用 M1：用户看到的是「这个项目我能不能申」，不是「它有几条原因」。按原因计会让 `au-407-training` 这种双因项目被数两次，把一个项目的事说成两个。
2. **`可修` 用「存在一条乙因」而不是「全部原因都是乙」。** 见 §1.1 规则 5，这是防洗白的第一道闸：混合项目按债计，逼着把可修的那条修掉。
3. **分母固定为全项目数 `|P|`，不改成「可判项目数」。** 若分母只算「能给出结论的项目」，删项目/放宽判定都能让比率变好看；固定分母让「多一个项目」永远只可能稀释、不可能美化。
4. **只判 `state == "unknown"`。** `gap`（差什么，差多少可知）与 `cannot`（明确不符）不是不可判，不占分子——这条与原口径一致，不动。

### 2.2 阈值：**1/3，一个数字都不改**

| 项 | 值 |
|---|---|
| 硬闸阈值 | `1/3`（不变） |
| 以 41 项折算 | 允许乙类最多 **13 项**（13/41 = 0.3171 ≤ 1/3；14 项 = 0.3415 即越线） |
| 当前实测 | C 乙类 **11 项**（0.2683），余量 **2 项** |
| 甲类软线 | **≥ 5 项**（0.1220）报警；当前 3 项（0.0732） |

**为什么是 1/3 而不是放宽到 2/5 或按新口径重算一个更好看的数**——回溯这条线当初是防什么（引自 `docs/audit/2026-11-12-match-readiness.md` §6、`docs/audit/2026-11-14-P2-0-未结构化漏网清零.md` §2–§3，均为仓库内既有记录）：

- 它防的第一件事是**「静默判过」**：note 里写了硬门槛、判定器一个字没读，用户被放行。`2026-11-14-P2-0` §2 站规第 1 条原话是「note 载有结构化字段表达不了的要求时，判定必须降级为「不可判 / 差什么」并给理由，**永不静默判过**」。
- 它防的第二件事是**「数据债失控」**：大量项目因为仓内没登记分数线/金额/名单而给不出结论，产品事实上不可用。

对着这两条看甲类：`edu_by_sponsor` 与 `age_unknown` **既不是静默判过（它们显式降级、带 `why`），也不是数据债（补数据消不掉，见 §1.2 #6 #13 #14）**。它们是被闸门误伤的那一类。所以：

> **1/3 从未被真正突破过。被突破的是度量口径——它把「诚实的、消不掉的不知道」和「我们欠的债」加在一起算。**拆开之后 C 的乙类率 0.2683 说明：原意下的闸门一直是绿的，红的是尺子。

反过来说，为什么不能干脆**提高**阈值（比如 2/5）：乙类 11 项意味着**四分之一以上的项目今天还给不出结论**，这是实打实的债；把阈值提到 2/5，等于宣布「再烂 5 个项目也能发版」，与 P2-0 立下的「不可判只许减不许增」直接冲突。**改口径是校准，改阈值是让步，两者不能混着做。**

### 2.3 备选方案对比（为什么否掉另外三种）

| 方案 | 分子 | C 值 | 否掉的理由 |
|---|---|---|---|
| A. 维持原样（全口径 1/3） | 全部 unknown | 0.3415 ❌ | 长期红；且逼团队在「让 CI 变绿」与「不许硬判」之间二选一，最后一定是硬判——**这条线会自己制造它想防的错误** |
| **B. 只绑乙类，1/3（建议）** | 可修项 | **0.2683 ✅** | 保留原阈值与原分母；甲类单列报告。唯一成本是需要 code 级登记（§4 已给防滥用办法） |
| C. 加权（甲算 0.5 个） | 乙 + 0.5×甲 | 0.3050 | 权重是拍脑袋的，无法向任何人解释「为什么甲类值半个项目」；而且它同样允许甲类悄悄吃掉余量 |
| D. 双硬闸（乙 1/3 + 甲 1/10） | — | 甲 0.0732 差 0.0268 就红 | 甲类硬闸会把「模型表达力不足」变成停工理由，而这件事的解法是评审，不是停工。改为**软线 5 项**（§2.2），保留可见性又不制造假停工 |

## 4. 风险与反对意见

### 4.1 滥用口子（按危险程度排序）

| # | 口子 | 怎么被滥用 | 防滥用办法 |
|---|---|---|---|
| R1 | **把乙塞进甲以绕闸**（最大） | 数据债修不动，就把某个 `silent` code 说成「设计性」，分子立刻变小、闸门变绿 | ① 登记**按 code 不按项目**——要洗白一个项目得先洗白一个 code，影响面立刻可见；② `test_every_silent_code_is_classified` 让未登记 code 直接红；③ 每个甲类 code 必须在 §1.2 有「为什么补字段也判不了」的一行论证，且论证要能回答「加什么字段就能判」；④ 甲类 code 的增删**须 Muse 复核**（不是自审）；⑤ 甲类软线 ≥5 项报警，让「甲类膨胀」在报告里刺眼 |
| R2 | **混合项目按甲报** | `de-chancenkarte` 有「认定」（甲）+「CEFR」（乙），若按主因报甲，可修的 CEFR 债就被藏了 | §1.1 规则 5「存在一条乙即算乙」写进 `undecidable_class()`，并用 `test_mixed_cause_program_counts_as_debt` 钉死该项目必须为 `avoidable` |
| R3 | **缩分母** | 删项目 / 合并项目 / 让 `judge()` 少返维，都能让比率变好看 | 分母固定为 `len(docs)`；已有 `test_flags_cover_every_program`（覆盖全项目）与 `test_json_output_is_parseable`（`total` == 目录文件数）兜着；建议再加一条 `assertEqual(rep["total"], 41)`，扩库时必须显式改，把「用新项目稀释」变成一次书面决定 |
| R4 | **私改阈值** | 把 1/3 改成 2/5，一劳永逸 | 阈值以字面量 `1 / 3` 硬编码在测试里（现状即如此），并加 `test_stop_line_message_matches_threshold` 咬住报告文案与常量同源 |
| R5 | **甲类变垃圾桶** | 模型表达力退化时，把「读不懂的 note」一律归设计性 | 甲类软线报警 + code 级登记 + 「甲类不得引入新 code 而不改文档」；再加一条硬约束：**甲类 code 的语义必须是「由第三方主体判断」或「官方无阈值」**，二者皆不满足的不许进 |
| R6 | **双口径打架** | 报告里两个数字并存，读者不知道谁在停工 | 报告与终端输出必须同行打印：`乙类 X%（闸门 1/3）｜全口径 Y%（仅记录）｜甲类 Z%（软线 5 项）`，并明写「闸门只看乙类」 |

### 4.2 反对意见与回应

**反对 1：「这不就是移动球门吗？」**
不是同一件事：阈值（1/3）、分母（41）、判据（`judge()` 的 `(dim, kind, code)`）三样**一个都没动**，动的是「分子里放哪一类」。而且新旧两个数字都输出、都钉测试、全口径还加了「只许不增」。如果 Muse 认为「统计口径变更」本身也需要预注册，**本文即预注册文本**——它先于任何代码改动存在，且写明了判据、阈值、防滥用办法，可被事后逐条核对。

**反对 2：「用户看到『不可判』就是没答案，甲类凭什么免责？」**
免责的是**团队**，不是**用户**。甲类照样进报告、照样在界面显示「这条得你自己去问 Sponsor/官方」，用户侧不受益于把它算成债——把它算成债的唯一效果是逼团队硬判一个数字出来，而硬判正是 P2-0 站规禁止的「静默判过」。**要让甲类变少，正确的动作是提升表达力或明确告知，不是把它记成债。**

**反对 3：「3 个甲类里有 2 个是 `age_unknown`，太依赖这一个 code 的归类了。」**
成立，已在 §1.4 摊开：若 `age_unknown` 判乙，C 乙类率 0.3171，余量只剩 0.0163（不到 1 个项目）。**这条应直接交 Muse 裁决**，而不是由本提案自行定案。裁决结果只影响分类，不影响公式结构（改 `BY_DESIGN_CODES` 一行即可）。

**反对 4：「甲类不设闸，会不会最后 41 个项目全是甲类，闸门形同虚设？」**
会，所以才有软线 5 项。但更根本的防线是 R5：甲类 code 的准入语义很窄（第三方主体判断 / 官方无阈值），而 41 个项目里绝大多数要求（分数线、金额、学历层级、居住地）都是**可表达的**。真出现甲类膨胀，说明是 note 语义读不懂，那本来就该停下来看，而不是让闸门替它背锅。
